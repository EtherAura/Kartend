# ThreadSanitizer suppressions for known third-party / Qt-internal false
# positives. See docs/dev/sanitizer-suppressions.md for the suppression
# policy + audit notes (Kartend-3hjs.2). Each block below cites a closed
# bd issue documenting the group's rationale.
#
# https://github.com/google/sanitizers/wiki/ThreadSanitizerSuppressions

# ─── Group A: Qt internal event-queue mutex (Kartend-feqz) ──────────────
# Qt synchronises queued-connection post→consume through the event
# queue's QMutex, but QMutex's fast path is futex/atomic-based — not a
# pthread_mutex TSan intercepts — so the happens-before edge is invisible.
# TSan reports the queued-arg malloc on the posting thread as racing
# with the queued-arg free on the consuming thread, even though Qt's
# internal lock fully orders them. None of these are fixable in Kartend
# code; re-evaluate when CI bumps Qt to a version that exposes the
# QMutex futex acquire/release as TSan-visible atomics.

# Qt::BlockingQueuedConnection slot dispatch: main thread heap-allocates a
# QSlotObject and the worker thread reads its vtable. Synchronisation is
# inside Qt's QMetaObject (via internal QMutex) and isn't visible to TSan.
race:QtPrivate::QSlotObject

# QObject::deleteLater() Qt event-queue lifecycle: deleteLater allocates a
# deferred-deletion QEvent on the calling thread, posts it onto the
# target object's thread, and the target's event loop frees it via
# QCoreApplicationPrivate::sendPostedEvents. Qt synchronises via the
# event-queue mutex, but the new/delete pair on the bare QEvent struct
# isn't observable to TSan as happens-before.
race:QObject::deleteLater
race:QCoreApplicationPrivate::sendPostedEvents

# Queued-connection arg lifecycle across the event-queue boundary: main
# thread allocates the slot args via QMetaType::create (operator new + copy
# ctor) into the QMetaCallEvent payload and the worker thread consumes
# them via QMetaType::destroy (~QList → QArrayDataPointer::deref → operator
# delete) after dispatching the slot. Surfaces under
# test_databasemanager's destruct-mid-scan test, which exercises teardown
# while the worker is still draining queued events.
race:QMetaCallEvent
race:QArrayDataPointer<CollectionConfig>::deref
race:QArrayDataPointer<CollectionContext>::deref

# ScrapeWriteWorker (and similar moveToThread'd QObject workers) receive
# queued signals carrying heap-allocated payloads. Same Qt event-queue-mutex
# happens-before edge as the QMetaCallEvent suppression above, but the
# specific symbol on this stack is QMetaType::create.
race:QMetaType::create

# Queued QMetaObject::invokeMethod(obj, functor): the calling thread
# heap-allocates a QtPrivate::QFunctorSlotObject wrapping the functor,
# posts it to the target object's thread, and that thread runs it. Qt
# orders the post-then-run pair through the event-queue mutex but its
# fast path is futex/atomic-based — not a pthread_mutex TSan intercepts.
race:invokeMethod

# QNetworkAccessManager → main-thread queued QByteArray payload: the QNAM
# thread allocates the response body via QByteArray::QByteArray and Qt
# queues it across to the main-thread slot via the meta-call event queue.
# Same fundamental pattern as the queued-arg suppressions above, but the
# visible top frames on this stack are QByteArray-specific.
race:QByteArray::reallocData
race:QByteArray::QByteArray

# ScrapeWriteWorker cross-thread queued writeCompleted signal: the worker
# thread runs `emit writeCompleted(requestId, ok)` inside performWrite, which
# heap-allocates the QMetaCallEvent argument payload via operator new on the
# worker thread; the main-thread event loop then reads that payload when it
# dispatches the connected slot (QtPrivate ...::call). Qt orders the
# post→dispatch pair through the event-queue QMutex (same futex/atomic fast
# path as the QMetaCallEvent / QMetaType::create entries above), but the
# allocation/read pair on the payload isn't observable to TSan as
# happens-before. The only Qt-named frame the stripped libQt6Core leaves on
# the racing stack is the emit site, so the suppression anchors there. This is
# inherent to receiving any cross-thread queued signal — not specific to how
# the test waits (it uses a QEventLoop + Qt::QueuedConnection, no QSignalSpy).
race:Scraper::ScrapeWriteWorker::performWrite

# ─── Group B: Qt thread lifecycle (Kartend-8fh5) ────────────────────────
# QThread::wait + QFuture::waitForFinished provably synchronise the worker
# thread before destructors proceed, but libQt6Core's stripped frames
# hide the happens-before edge from TSan. The QtConcurrent thread pool
# also reuses worker threads, so the access-history buffer keeps stale
# addresses from the previous task and the next task on the same pooled
# thread appears racy against the previous one's COW operations.

# QueryManager destructor races: the destructor runs on the worker thread
# (Qt deleteLater pattern), tearing down member state — the shared_ptr<
# atomic_bool> control block, the QObject base, etc. — while the owning
# DatabaseManager / test fixture on the main thread is still inside
# requestCancelScan() or QObject::~QObject() reading those same members.
# The atomic_bool itself is correctly synchronized via memory_order; the
# control-block / vtable teardown isn't observable to TSan as a
# happens-before edge across the deleteLater dispatch boundary.
race:QueryManager::~QueryManager
race:_Sp_counted_ptr_inplace
race:_Sp_counted_base

# QWaitCondition / QMutex tear-down at process exit: ApplicationManager
# owns a QWaitCondition that's torn down from MainWindow::~MainWindow on
# the main thread. TSan flags pthread_cond_destroy / pthread_mutex_destroy
# against earlier waits on a worker thread that has already returned.
race:pthread_cond_destroy
race:pthread_mutex_destroy
race:QWaitCondition::~QWaitCondition

# QtTest's per-test "QtTest Watchdog" thread waits on a pthread_cond_t for
# the test-timeout signal. When the test finishes, qExec cancels the
# watchdog and frees its cond_var/mutex — but TSan flags the
# pthread_cond_wait (which has already returned) as racing with operator
# delete in the qRun teardown. Surfaces under CPU contention only.
race:QTest::qRun

# Qt copy-on-write data structures (QHash, QString, QByteArray, ...)
# allocate their underlying buffers via QArrayData::allocate, often from
# a worker QThread. Once the worker finishes and is joined, main thread
# later frees the buffer through normal RAII (DatabaseManager /
# QueryManager destructors). TSan can't establish the happens-before
# edge through Qt's QThread::wait into the thread's earlier malloc.
race:QArrayData::allocate

# Realloc / detach path of the same COW buffers. When two QtConcurrent::run
# tasks (BatchScrapeRunner::applyAndFinish dispatches one per item)
# capture QString / QList members of the runner by value, the captures
# share the COW source buffer. Pool-reuse artifact, not a real race.
race:QArrayData::reallocateUnaligned

# CacheManager::initialize() runs on a QtConcurrent::run worker thread.
# ApplicationManager::~ApplicationManager() calls m_cacheInitFuture
# .waitForFinished() before tearing the CacheManager down. TSan still
# flags a race because Qt's QFuture::reportFinished -> waitForFinished
# acquire chain doesn't propagate happens-before into the QMutex unlock
# atomic that the worker did *inside* the now-freed CacheManager.
race:CacheManager::initialize

# Same teardown race seen from the destructor side: the QtConcurrent
# cache-init lambda in ApplicationManager::initialize reads CacheManager
# state while CacheManager::~CacheManager frees it.
race:CacheManager::~CacheManager

# ArtworkLoadDispatcher::dispatchBatch worker-thread lambda teardown:
# QtConcurrent::run dispatches a worker that captures a QList<ArtworkInfo>
# by move. When the worker returns, the captured QList destructs on the
# pool worker thread, freeing each ArtworkInfo — which holds a
# QPointer<ItemWidget>. The QPointer's underlying QWeakPointer atomically
# derefs a refcount in the ItemWidget's d-pointer. Meanwhile the test's
# main thread is qDeleteAll()-ing the same ItemWidgets.
race:ArtworkInfo::~ArtworkInfo

# HttpClient::drainHost first-use spin-up of QNetworkAccessManager's
# internal QThread 'QNetworkAccessM': the first send() in the lifetime
# of a test process triggers Qt's lazy QNAM thread initialisation. Qt's
# QThread::start / QThread::wait pair synchronises this, but the
# libQt6Core frames between pthread_create and the QNAM thread body are
# stripped. Only the start-up window of a fresh QNAM is racy.
race:Scraper::HttpClient::drainHost

# ─── 2026-06-10 audit wave: per-site hand-off anchors (Kartend-felhb) ───
# New tests/code from the 2026-06 audit exercise the same two
# uninstrumented-Qt false-positive classes as Groups A/B — Qt orders the
# hand-off through futex/atomic fast paths (event-queue QMutex, QThreadPool
# queue mutex, QReadWriteLock d_ptr CAS, QtConcurrent ThreadEngineBarrier)
# that TSan cannot intercept, so the allocation-write on the posting thread
# appears to race the first worker-side read. Each entry below anchors on
# the narrowest Kartend-visible (or inlined-template) symbol its report
# leaves after libQt6* strips its own frames.

# QtConcurrent::blockingMap inline kernel teardown: startMap heap-allocates
# a MapKernel/IterateKernel (template code compiled into our binary, so the
# symbols are visible); pooled workers read the kernel vptr in
# forThreadFunction / shouldStartThread while the last finisher destroys it
# via ThreadEngine::asynchronousFinish. The last-thread-out ordering is
# ThreadEngineBarrier's atomic semaphore inside uninstrumented
# libQt6Concurrent — invisible to TSan. Surfaces under
# DirectoryCache::processQueuedDirectories / prewarmDirectories
# (test_directorycache, bench_artworkresolve).
race:QtConcurrent::ThreadEngine

# ScanWorkController queued-runnable hand-off (Kartend-t2my8 test): the test
# news CountingTask runnables on the main thread and ScanWorkController's
# QThreadPool::start hands them to pooled workers; the worker's first read
# of the runnable's members appears to race the allocation-write because
# QThreadPool's queue QMutex fast path is futex-based. The test
# intentionally synchronises through pool internals (that IS the contract
# under test), so the hand-off edge cannot be made TSan-visible.
race:TestScanWorkController::testQueuedTasksStillRunAfterCancel

# Startup orphan purge queued onto the DB worker (Kartend-dbqt5):
# DatabaseManager::purgeOrphanCollectionData copies the live-uuid QSet into
# a std::function on the GUI thread and posts it to the worker thread via
# queueWorkerWrite -> QMetaObject::invokeMethod; the worker's first read of
# the capture (liveUuids.isEmpty()) races the capture-copy allocation across
# the event-queue boundary. Same class as Group A's invokeMethod entry, but
# this report's stacks inline/strip every Qt frame, leaving only the
# Kartend purge symbols to anchor on.
race:purgeOrphanRowsOnConnection

# ArtworkLoadDispatcher abandon-path teardown (Kartend-xoftg): the dtor's
# bounded ArtworkDispatcherCacheHandle::invalidate() calls
# m_pinLock.tryLockForWrite while an abandoned worker still holds the read
# pin. The contended QReadWriteLock inflates to a QReadWriteLockPrivate
# drawn from Qt's global freelist — whose backing operator new[] block is
# first allocated by the destructing (main) thread — and the worker's later
# unlock() locks the private's std::mutex inside that block. The private is
# published through QReadWriteLock's d_ptr atomic CAS in uninstrumented
# libQt6Core, so TSan sees no happens-before edge. Verified 2026-06-11: the
# abandoned task touches ONLY the shared_ptr-co-owned handle (m_pinLock +
# the nulled m_cacheManager atomic), never freed dispatcher or pool memory.
race:ArtworkLoadDispatcher::~ArtworkLoadDispatcher

# Same freelist artifact, surfaced as a mutex report instead of a race:
# the worker's m_pinLock.unlock() goes through the inflated
# QReadWriteLockPrivate's wait-condition pthread mutex, which TSan first
# observes at that unlock (the private was published through the d_ptr CAS
# it can't see), so it reports "unlock of an unlocked mutex (or by a wrong
# thread)". The lock/unlock pairing in tryLoadFromDiskCache is structurally
# correct (tryLockForRead checked, early return on failure).
mutex:ArtworkDispatcherCacheHandle::tryLoadFromDiskCache

# Cache-init QtConcurrent::run hand-off: ApplicationManager::initialize
# news the StoredFunctionCall task object on the GUI thread and
# QThreadPool::start hands it to a pooled worker, whose very first read at
# RunFunctionTaskBase::run() entry (QFutureInterface state) appears to race
# the allocation-write — the pool-queue QMutex's futex fast path provides
# no TSan-visible edge. Companion of Group B's CacheManager::initialize
# entry (that one anchors the worker-side frames; this report's racing
# stacks only keep the dispatch site). Anchoring on the dispatch site
# rather than RunFunctionTaskBase keeps every other QtConcurrent::run
# functor body fully visible to TSan. Surfaces under the MainWindow
# integration fixtures (TestNavigationManager, TestLaunchFlow).
race:ApplicationManager::initialize

# Same StoredFunctionCall dispatch-site hand-off for the per-item media
# write: BatchScrapeRunner::applyAndFinish QtConcurrent::run's the write
# task on the GUI thread and the pooled worker's first read at
# RunFunctionTaskBase<MediaWriteResult>::run() entry races the allocation.
# Surfaces intermittently under test_batchscraperunner.
race:Scraper::BatchScrapeRunner::applyAndFinish

# Consume-side counterpart of Group A's QMetaType::create entry: the
# main thread copies a queued signal's payload via QMetaType::construct
# (ScrapedItem copy-ctor into the QMetaCallEvent) and the worker thread
# frees the previous payload via QMetaType::destroy after dispatching the
# slot; the event-queue mutex ordering both is futex-based and invisible.
# Surfaces intermittently under test_scrapewriteworker.
race:QMetaType::destroy

# Launch usage-stats completion hop (Kartend-cbtml):
# DatabaseManager::recordItemLaunch queues its write to the DB worker; the
# worker then copies the onCompleted std::function into the queued
# main-thread hop (databasemanager_items.cpp invokeMethod(qApp, ...)), and
# the main thread's later read of the captured QStrings races that copy
# across the event-queue boundary. The lambda's enclosing-function name is
# embedded in the symbolized std::function/_M_create template frames on
# both stacks, so the suppression anchors there.
race:DatabaseManager::recordItemLaunch

# Placeholder-tile render: QPixmap::fromImage inside
# ItemPlaceholderRenderer::buildTile triggers Qt Gui's multithreaded image
# conversion, which fans segments out to global-pool threads synchronised
# by a QSemaphore (futex fast path, invisible to TSan). Surfaces as the
# main thread's tile allocation racing a pooled worker's buffer free
# (TestNavigationManager); buildTile is the only named frame the racing
# stacks keep.
race:ItemPlaceholderRenderer::buildTile

# QThreadPool queue churn between two pooled workers: enqueueTask's
# operator new of a queue node vs another pooled thread's operator delete
# when it dequeues — ordered by the pool's QMutex (futex fast path,
# invisible). Both stacks are otherwise stripped libQt6Core frames;
# enqueueTask is the lone exported symbol to anchor on. Surfaces under
# DirectoryCache's nested QtConcurrent prewarm.
race:QThreadPoolPrivate::enqueueTask

# QThreadPool per-thread QWaitCondition lifecycle: one pooled worker
# constructs the wait condition (operator new inside QWaitCondition's
# ctor) while another worker's wakeOne locks its internal mutex; the
# hand-off is the pool's QMutex again. Ctor-side counterpart of Group B's
# ~QWaitCondition entry. Surfaces under DirectoryCache / BenchArtworkResolve
# global-pool fan-out.
race:QWaitCondition::QWaitCondition

# Qt-internal pool bookkeeping with EVERY frame stripped (e.g. two pooled
# workers' memmoves on a recycled QArrayData block inside libQt6Core's
# QThreadPool code, or libQt6Gui's threaded image-conversion buffer free):
# no race: symbol pattern can target these because GCC's libtsan matches
# suppressions only against the racing-access stacks, and those contain
# nothing but <null> libQt6* frames (the CI image's Qt is stripped).
# called_from_lib matches by MODULE, so it works on stripped libraries and
# suppresses only interceptor events whose caller is inside the named .so —
# Kartend's instrumented code stays fully visible, including Qt template
# code inlined into Kartend TUs from headers. Same rationale and tradeoff
# as the module-scoped Group D on the in-flight Kartend-t9u0o branch (these
# two lines converge with it textually; dedup is a no-op at merge). The
# narrower race: entries above are kept deliberately: they anchor on
# Kartend-visible symbols, cost nothing, and document the known shapes.
# Surfaces under Integration.TestNavigationManager / TestLaunchFlow
# (MainWindow fixture spins the global pool via cache init + placeholder
# tile conversion).
called_from_lib:libQt6Core.so.6
called_from_lib:libQt6Gui.so.6

# ─── Group C: Third-party library sync primitives (Kartend-d4x4) ────────
# These libraries use sync primitives TSan can't observe; the races
# originate inside them. None are fixable in Kartend code; re-evaluate
# when CI bumps the third-party dep or when the Qt Multimedia backend
# switches off PulseAudio + GStreamer (e.g. to ffmpeg).

# QThread + glib GMainContext wakeup: GMainContext writes to an eventfd
# from the worker thread to wake the main loop, and the main thread reads
# it on shutdown. glib's internal mutex covers this but the eventfd
# handle write itself isn't ordered against the read in a way TSan can
# observe.
called_from_lib:libglib-2.0.so

# QtMultimedia / PulseAudio backend: VideoPreviewWidget construction
# triggers QPlatformMediaIntegration which spawns PulseAudio's
# threaded-ml thread. All races here are inside libpulsecommon
# (pa_mutex_lock vs pa_xmalloc on the threaded-ml thread); pulseaudio
# uses its own sync primitives that TSan can't observe.
called_from_lib:libpulsecommon

# QtMultimedia / GStreamer backend: VideoThumbnailExtractor and other
# media widgets fall through to the gstreamer backend on Linux when
# ffmpeg isn't selected. gstreamer manages its own per-thread allocators
# and frees on pipeline tear-down from a worker thread that TSan can't
# reason about.
called_from_lib:libgstreamer-1.0.so

# ─── Group D: Qt shared libraries, module-scoped (Kartend-t9u0o) ────────
# CI's Qt (Ubuntu qt6-base, stripped, NOT TSan-instrumented) can only ever
# surface races through intercepted calls (malloc/free, memcpy/memmove,
# pthread_*) made FROM its own code: its plain loads/stores are invisible
# to TSan, and its sync primitives' futex/atomic fast paths provide no
# happens-before edge TSan can observe. Such reports are therefore
# inherently un-orderable half-edges — Qt-internal pool-lifecycle churn
# (QThreadPool / QWaitCondition / QtConcurrent ThreadEngine setup +
# teardown), pooled-thread COW-buffer recycling, QNAM's lazy worker-thread
# start-up, QScrollArea's reserved render threads — with every frame
# stripped, so no race: symbol pattern can target them (the CI image has
# no llvm-symbolizer; Qt frames render <null>).
#
# called_from_lib matches by MODULE, not symbol, so it works on stripped
# libraries. It suppresses only interceptor events whose caller is inside
# the named .so — Kartend's instrumented code stays fully visible,
# INCLUDING Qt container/template code inlined into Kartend TUs from
# headers (that code compiles into the test binary, not libQt6*). This is
# what lets the previously QSKIP'd concurrency tests (DatAudit::run
# fan-out, the parallel recursive scan, BatchScrapeRunner dispatch,
# TitleFilter lock hammering, HttpClient/QNAM, ScrapeWriteWorker
# teardown) run instrumented under TSan instead of being skipped
# wholesale: a racy worker lambda touching Kartend data still fires.
#
# Tradeoff, accepted deliberately: a genuine race where the Qt side of the
# pair performs its access via an out-of-line interceptor call inside
# libQt6* is muted — but those reports were already undiagnosable
# (half-edge, all-stripped frames) and previously cost us the entire test
# under QSKIP. The narrower race: entries in Groups A–B are kept even
# where this overlaps: they anchor on Kartend-visible symbols, cost
# nothing, and document the known shapes individually.
called_from_lib:libQt6Core.so.6
# QScrollArea::show() reserved render-thread teardown (see
# test_viewportschedulermath's former skip rationale).
called_from_lib:libQt6Gui.so.6
# QNetworkAccessManager lazy worker-thread start-up window (see
# test_httpclient's former skip rationale).
called_from_lib:libQt6Network.so.6

# ─── Group D2: Qt template internals inlined into instrumented binaries ──
# (Kartend-t9u0o, round 2 — dispatch run 27278690648.) QtConcurrent's kernel
# machinery is header-only, so it compiles INTO the test binaries where
# called_from_lib cannot reach. Its task hand-off (QThreadPool queue) and
# result plumbing are futex-ordered — invisible to TSan — yielding two
# false-positive shapes. CAUTION for future entries: TSan matches a race
# suppression against EVERY frame of BOTH racing stacks, and worker-lambda
# execution stacks always contain RunFunctionTaskBase::run() /
# threadFunction() / forThreadFunction() — anchoring on any of those (or on
# the header file names) would mute REAL races in Kartend worker code, which
# is exactly the coverage this exercise restores. Anchor ONLY on frames that
# never appear during user-code execution:
#
# Task creation vs first virtual call (ctor-write vs vptr-read in
# RunFunctionTaskBase<T>::run()): the launching thread's operator-new/ctor
# is futex-ordered against the pool thread's first use. Anchored on the
# CREATION-side resolver frame (qtconcurrentstoredfunctioncall.h), which has
# returned before the functor ever runs.
race:NonPromiseTaskResolver
# Kernel teardown vs worker wind-down (~MappedEachKernel / ~SequenceHolder1
# vptr write vs forThreadFunction read; reached only via ThreadEngine::
# asynchronousFinish after every iteration has completed). Iteration-time
# frames are deliberately NOT suppressed.
race:asynchronousFinish
race:~MappedEachKernel
race:~SequenceHolder1
# Pool-reuse COW deref — further specializations of the Group B
# QArrayDataPointer entries (same rationale; kept template-narrow on
# purpose: the deref frame is also the top frame of a REAL shared-container
# race, so each specialization is admitted only after manual triage).
race:QArrayDataPointer<std::pair<QString, QString>>::deref
race:QArrayDataPointer<Scraper::MediaAsset>::deref

mutex:test_titlefilter
