# ThreadSanitizer suppressions for known third-party / Qt-internal false
# positives. See https://github.com/google/sanitizers/wiki/ThreadSanitizerSuppressions

# Qt::BlockingQueuedConnection slot dispatch: main thread heap-allocates a
# QSlotObject and the worker thread reads its vtable. The synchronization
# happens inside Qt's QMetaObject (via internal QMutex) and isn't visible
# to TSan, so the read/write of the slot object pointer looks like a race.
race:QtPrivate::QSlotObject

# QThread + glib GMainContext wakeup: GMainContext writes to an eventfd from
# the worker thread to wake the main loop, and the main thread reads it on
# shutdown. glib's internal mutex covers this but the eventfd handle write
# itself isn't ordered against the read in a way TSan can observe.
called_from_lib:libglib-2.0.so

# QtMultimedia / PulseAudio backend: VideoPreviewWidget construction triggers
# QPlatformMediaIntegration which spawns PulseAudio's threaded-ml thread. All
# races here are inside libpulsecommon (pa_mutex_lock vs pa_xmalloc on the
# threaded-ml thread); pulseaudio uses its own sync primitives that TSan
# can't observe.
called_from_lib:libpulsecommon

# QtMultimedia / GStreamer backend: VideoThumbnailExtractor and other media
# widgets fall through to the gstreamer backend on Linux when ffmpeg isn't
# selected. gstreamer manages its own per-thread allocators and frees on
# pipeline tear-down from a worker thread that TSan can't reason about.
called_from_lib:libgstreamer-1.0.so

# QueryManager destructor races: the destructor runs on the worker thread
# (Qt deleteLater pattern), tearing down member state — the shared_ptr<
# atomic_bool> control block, the QObject base, etc. — while the owning
# DatabaseManager / test fixture on the main thread is still inside
# requestCancelScan() or QObject::~QObject() reading those same members.
# The atomic_bool itself is correctly synchronized via memory_order; the
# control-block / vtable teardown isn't observable to TSan as a
# happens-before edge across the deleteLater dispatch boundary.
race:QueryManager::~QueryManager
race:_Sp_counted_ptr_inplace
race:_Sp_counted_base

# QWaitCondition / QMutex tear-down at process exit: ApplicationManager
# owns a QWaitCondition that's torn down from MainWindow::~MainWindow on
# the main thread. TSan flags pthread_cond_destroy / pthread_mutex_destroy
# against earlier waits on a worker thread that has already returned.
race:pthread_cond_destroy
race:pthread_mutex_destroy
race:QWaitCondition::~QWaitCondition

# QObject::deleteLater() Qt event-queue lifecycle: deleteLater allocates
# a deferred-deletion QEvent on the calling thread, posts it onto the
# target object's thread, and the target's event loop frees it via
# QCoreApplicationPrivate::sendPostedEvents. Qt synchronizes via the
# event-queue mutex, but the new/delete pair on the bare QEvent struct
# isn't observable to TSan as happens-before — the event memory looks
# allocated on one thread and freed on another with no visible edge.
race:QObject::deleteLater
race:QCoreApplicationPrivate::sendPostedEvents

# QtTest's per-test "QtTest Watchdog" thread waits on a pthread_cond_t for
# the test-timeout signal. When the test finishes, qExec cancels the
# watchdog and frees its cond_var/mutex — but TSan flags the
# pthread_cond_wait (which has already returned) as racing with
# operator delete in the qRun teardown. Qt synchronizes via QThread::wait
# internally, but TSan can't observe the happens-before edge through the
# mid-wait cancel. Surfaces under CPU contention only (e.g. parallel act
# runners on a single host); on a dedicated CI runner with 4 vCPUs the
# main thread is fast enough that the watchdog has fully exited before
# delete, so the race doesn't materialise.
race:QTest::qRun

# Qt copy-on-write data structures (QHash, QString, QByteArray, ...) all
# allocate their underlying buffers via QArrayData::allocate, often from a
# worker QThread. Once the worker finishes and is joined, main thread later
# frees the buffer through normal RAII (DatabaseManager / QueryManager
# destructors). TSan can't establish the happens-before edge through Qt's
# QThread::wait into the thread's earlier malloc, so the cross-thread
# malloc/free pair lights up as a race even though the join is sound.
# Suppressing here catches all variants of this pattern across test
# binaries (test_databasemanager, test_integration, …).
race:QArrayData::allocate
# Realloc / detach path of the same COW buffers. When two QtConcurrent::run
# tasks (BatchScrapeRunner::applyAndFinish dispatches one per item) capture
# QString / QList members of the runner by value, the captures share the
# COW source buffer. The underlying QArrayData operations (reallocateUnaligned
# during string growth, memmove during list resize) happen on separate
# allocator slots per task, but the QtConcurrent thread-pool worker keeps
# the same heap addresses in its TSan access history across consecutive
# tasks, so the next task on the same pooled thread looks racy against the
# previous one's COW operations. Pool-reuse artifact, not a real race.
race:QArrayData::reallocateUnaligned

# Queued-connection arg lifecycle across the event-queue boundary: when
# DatabaseManager emits a queued signal carrying CollectionConfig /
# CollectionContext / QList<CollectionConfig> args, main thread allocates
# them via QMetaType::create (operator new + copy ctor) into the
# QMetaCallEvent payload and the worker thread consumes them via
# QMetaType::destroy (~QList → QArrayDataPointer::deref → operator
# delete) after dispatching the slot. Qt synchronises post/consume
# through the event-queue mutex inside QCoreApplication::sendPostedEvents,
# but TSan can't observe the edge through libQt6Core's stripped frames so
# both sides look like an unsynchronised malloc/free pair on the same
# heap slot. Surfaces under test_databasemanager's destruct-mid-scan test,
# which is specifically designed to exercise teardown while the worker
# is still draining queued events.
race:QMetaCallEvent
race:QArrayDataPointer<CollectionConfig>::deref
race:QArrayDataPointer<CollectionContext>::deref

# ScrapeWriteWorker (and similar moveToThread'd QObject workers) receive
# queued signals carrying heap-allocated payloads. Main thread allocates
# the slot args via QMetaType::create (operator new); the worker's
# moc-generated qt_static_metacall reads them after Qt dispatches the
# QMetaCallEvent on the worker's event loop. Same Qt event-queue-mutex
# happens-before edge as the QMetaCallEvent suppression above, but the
# specific symbol on this stack is QMetaType::create — the libQt6Core
# frames between create() and the moc metacall are stripped, so TSan
# never sees the synchronising mutex.
race:QMetaType::create

# CacheManager::initialize() runs on a QtConcurrent::run worker thread.
# ApplicationManager::~ApplicationManager() calls m_cacheInitFuture
# .waitForFinished() before tearing the CacheManager down, so the worker
# has provably finished by the time the destructor proceeds. TSan still
# flags a race because Qt's QFuture::reportFinished -> waitForFinished
# acquire chain doesn't propagate happens-before into the QMutex unlock
# atomic that the worker did *inside* the now-freed CacheManager — the
# QtConcurrent thread pool's persistent worker keeps the address in its
# access-history buffer, and the next test's CacheManager (allocated
# at the same heap slot via allocator reuse) appears to race with the
# previous worker's mutex unlock.
race:CacheManager::initialize
# Same teardown race seen from the destructor side: the QtConcurrent
# cache-init lambda in ApplicationManager::initialize reads CacheManager
# state while CacheManager::~CacheManager frees it. ApplicationManager's
# destructor calls m_cacheInitFuture.waitForFinished() before the
# m_cacheManager unique_ptr is destroyed (applicationmanager.cpp:52), so the
# worker has provably finished — but TSan can't see the QFuture wait's
# happens-before edge. CacheManager::initialize is inlined into the
# QtConcurrent lambda and never appears as its own frame, so the destructor
# symbol is matched instead.
race:CacheManager::~CacheManager

# Queued QMetaObject::invokeMethod(obj, functor): the calling thread heap-
# allocates a QtPrivate::QFunctorSlotObject wrapping the functor, posts it
# to the target object's thread, and that thread runs it. Qt orders the
# post-then-run pair through the event queue's QMutex, but QMutex's fast
# path is futex/atomic-based — not a pthread_mutex TSan intercepts — so the
# functor's construction (calling thread) and execution (target thread)
# look unsynchronised. The functor-call machinery in qobjectdefs_impl.h is
# symbolised by TSan only as bare template names (`impl`, `call`) that no
# stable suppression can match, so this matches the invokeMethod frame on
# the allocating side instead. Surfaces across the QueryManager scan tests,
# which drive the worker-thread QueryManager via
# invokeMethod(qm, lambda, Qt::QueuedConnection).
race:invokeMethod

# ArtworkLoadDispatcher::dispatchBatch worker-thread lambda teardown:
# QtConcurrent::run dispatches a worker that captures a QList<ArtworkInfo>
# by move. When the worker returns, the captured QList destructs on the
# pool worker thread, freeing each ArtworkInfo — which holds a
# QPointer<ItemWidget>. The QPointer's underlying QWeakPointer atomically
# derefs a refcount in the ItemWidget's d-pointer. Meanwhile the test's
# main thread is qDeleteAll()-ing the same ItemWidgets, which decrefs the
# same atomic. Qt's QPointer machinery is thread-safe on the atomic ops
# themselves (qatomic_cxx11.h uses std::atomic with the right memory order),
# but TSan can't bridge the QtConcurrent worker's QFuture finish state to
# main's delete because the QFuture wait/cancel synchronisation is buried
# behind stripped libQt6Core frames. Surfaces under
# testDispatcher_cancelMidFlightSuppressesHandler where the cancel races
# the in-flight batch's d-pointer deref.
race:ArtworkInfo::~ArtworkInfo

# HttpClient::drainHost first-use spin-up of QNetworkAccessManager's
# internal QThread 'QNetworkAccessM': the first send() in the lifetime of
# a test process triggers Qt's lazy QNAM thread initialisation. The
# spawned thread mallocs its initial state on T_QNAM while the main
# thread is still inside drainHost; the same heap slot is later freed
# from T_QNAM via QNAM's internal teardown. Qt's QThread::start /
# QThread::wait pair synchronises this, but the libQt6Core frames between
# pthread_create and the QNAM thread body are stripped, so TSan can't
# observe the happens-before edge. Only the start-up window of a fresh
# QNAM is racy — once the thread is up, subsequent sends are fine.
race:Scraper::HttpClient::drainHost

# QNetworkAccessManager → main-thread queued QByteArray payload: the
# QNAM thread allocates the response body via QByteArray::QByteArray and
# Qt queues it across to the main-thread slot via the meta-call event
# queue. The receiver (a TestHttpClient slot) reallocs the QByteArray via
# QByteArray::reallocData when it mutates the copy. Qt's queued-connection
# arg lifecycle is synchronised through the event-queue mutex, but TSan
# can't observe the edge through the stripped libQt6Core frames between
# the queued post and the qt_static_metacall dispatch — so the cross-
# thread QArrayData buffer looks like an unsynchronised memcpy pair on
# the same heap slot. Same fundamental pattern as the
# race:QArrayData::allocate / race:QMetaType::create suppressions above,
# but the visible top frames on this stack are QByteArray-specific.
race:QByteArray::reallocData
race:QByteArray::QByteArray
