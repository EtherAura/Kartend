# Translation / i18n contributor workflow

Kartend uses Qt's Linguist toolchain. Source strings flow through
`tr(...)` calls in C++, get extracted to `.ts` (translation source)
files, and ship to users as `.qm` (compiled) files alongside the
binary.

This page covers the contributor side — both translators starting a
new language, and developers adding new translatable strings.

## Files

```
translations/
├── kartend_en.ts   # English source (canonical strings)
├── kartend_en.qm   # Compiled English (default)
└── (kartend_<lang>.ts / .qm added per language)

.lupdate/
├── <generated>     # lupdate cache / context files
```

User-facing translation files live in `translations/`. The
`.lupdate/` directory carries lupdate intermediate state — it's
checked in so contributors don't need to run a full re-extract on
clone.

## Refreshing translations after a string change

When you touch any `tr(...)` (add, edit, remove) you need to refresh
the `.ts` files so translators see the change.

```bash
.scripts/build.sh --maintenance --i18n-refresh
```

This runs `lupdate` across `src/` and updates each
`translations/kartend_*.ts`. Existing translations are preserved;
new strings appear as empty entries; obsolete strings get marked
**vanished** for translator cleanup.

Commit the refreshed `.ts` files alongside your code change. CI
**will** notice if you skip this step — the build job runs
`lupdate -no-obsolete -dry-run` and fails on drift.

## Starting a new language

1. **Pick a locale code.** Use the standard
   `<language>[_<COUNTRY>]` form, lowercase language, uppercase
   country: `fr`, `de`, `pt_BR`, `zh_CN`.
2. **Copy the English source as a seed.**

   ```bash
   cp translations/kartend_en.ts translations/kartend_<lang>.ts
   ```
   Then edit the new file: change the `<TS language="…">` attribute
   to your locale, blank out every `<translation>` element (or
   leave the English in if you want a pre-populated draft).

3. **Register the file** in
   [translations/CMakeLists.txt](../translations/CMakeLists.txt)
   (or wherever the translations are wired) so the build picks it
   up.

4. **Translate** in Qt Linguist
   (`linguist translations/kartend_<lang>.ts`) or any text editor
   — `.ts` is plain XML. Linguist gives you:

   - Source-string preview with context
   - Pluralization editor (when the source uses `tr(s, ctx, n)`)
   - "Mark as finished" workflow for tracking progress
   - In-context translation suggestions from a memory file

5. **Test locally:**

   ```bash
   .scripts/build.sh --maintenance --i18n-refresh   # ensure .qm is rebuilt
   LANG=<lang>.UTF-8 .scripts/build.sh --debug --run kartend
   ```

   Or, on systems where `LANG` doesn't override the Qt locale,
   set the Qt-specific env var:

   ```bash
   QT_LOCALE=<lang>_<COUNTRY> kartend
   ```

   Confirm the strings render in the new language. Long strings
   that overflow buttons / labels are the most common translation
   defect — eye-test every dialog.

6. **Submit** as a PR. Translation-only PRs are welcome and don't
   need a separate bd issue.

## Adding new translatable strings (developer side)

### The `tr(...)` family

```cpp
// In a QObject subclass:
label->setText(tr("Open"));

// In a non-QObject namespace / free function:
QString s = QCoreApplication::translate("MyContext", "Open");

// With a plural:
label->setText(tr("%n item(s)", "", count));

// With a disambiguating comment for the translator:
button->setText(tr("Open", "verb — perform action on a file"));
```

Conventions:

- **Always use `tr(...)`** for user-visible strings. The exceptions
  (debug logs, internal identifiers, file paths) shouldn't go through
  the UI in the first place.
- **Add a context comment** when the same English string could mean
  different things (`tr("Open", "verb")` vs `tr("Open", "adjective —
  not closed")`). Translators see the comment in Linguist.
- **Prefer `%1`, `%2`** numbered placeholders over string
  concatenation — translators need to reorder them in many
  languages. `tr("Failed to load %1 from %2").arg(file, src)` is
  right; `tr("Failed to load ") + file + tr(" from ") + src` is
  not.

### Pluralization

```cpp
tr("%n result(s)", "", count)
```

The `%n` placeholder pluralizes per the language's plural rules
(many languages have 2-form, some 3+, some 1). The middle `""` is
the disambiguation comment; if the same `%n` string could mean
different things, distinguish them.

Linguist's plural editor lets translators fill in each plural form
for the target language without C++ involvement.

### Don't translate

| Category | Why |
|----------|-----|
| Log messages (`qInfo() << ...`) | Logs are diagnostic — keeping them in English helps cross-locale bug reports |
| INI key names | They're a wire format |
| Filenames / paths | Not user-facing in the i18n sense |
| Debug output | Same as logs |
| Reserved identifiers (`favorites`, `is_smart`, scraper provider ids) | Stable identifiers, not user-facing text |

## Pulling translations during build

CMake compiles every `translations/kartend_<lang>.ts` into a
`kartend_<lang>.qm` and installs it next to the executable (or to
the system's locale dir on Linux). The application loads them via
`QTranslator::load(...)` keyed on `QLocale::system()`.

Running Kartend with the OS locale set to a translated language
picks up the matching `.qm` automatically. Falling back to English
when no translation exists is handled by Qt — untranslated entries
in a `.ts` file render in English.

## Updating an existing translation

When a string changes, `lupdate` flags the affected entry in every
`.ts` file as **fuzzy** — the previous translation is kept but
marked stale. Translators in Linguist see fuzzy entries with a
distinctive marker and can:

- Confirm the translation still applies → clear fuzzy flag.
- Update it → enter new text, clear fuzzy flag.
- Mark as obsolete → translation is dropped from the `.qm`.

Removed strings (the developer deleted the `tr(...)` call) get
moved to `<message>...<source>...</source><translation
type="vanished">...</translation></message>` entries. These don't
ship in the `.qm` but are preserved in the `.ts` so a future revert
of the source change recovers the translation.

## Locales the project actively maintains

| Locale | File | Maintainer |
|--------|------|------------|
| `en` | `kartend_en.ts` | Project default (canonical strings) |

Adding a new actively-maintained locale here is a documentation /
governance choice, not a technical one — once you've shipped a
non-trivial translation and committed to keeping it up to date,
add a row.
